# Jungle7 Mini React

### 협업 규칙

- **개발자 사용성** · 구현에 여러 선택지가 생기면 Mini React를 사용하는 개발자에게 편한 쪽을 선택
- **AI 활용 비용** · 적은 토큰으로 더 좋은 결과를 내는 것을 목표로, 토큰 사용량과 환산 비용을 함께 기록
- **구현 범위** · 매뉴얼에 합의한 범위 안에서 구현하고 ai가 기능을 임의로 추가하는 일을 방지

| ID | 우선 | 요구사항 | LMS 근거 |
| --- | --- | --- | --- |
| R1 | Must | 키로 값을 저장하고 조회할 수 있다 (해시 테이블 직접 구현) | 요구사항: 해시 테이블로 키-값 저장소 |
| R2 | Must | 보관 기간을 설정할 수 있고, 만료된 키는 찾을 수 없다 | 중점 2 |
| R3 | Must | 저장된 데이터를 삭제(무효화)할 수 있다 | 중점 4, 품질 |
| R4 | Must | 외부 프로그램이 API로 사용할 수 있다 | 요구사항, 중점 3 |
| R5 | Must | 동시에 요청이 와도 저장·조회·삭제 결과가 어긋나지 않는다 | 중점 1 |
| R6 | Must | 데이터가 많이 쌓여도 저장·조회·삭제 속도가 유지된다 | 요구사항: 해시 테이블 설계 원리 (해석에 따라 범위 밖) |
| R7 | Could | 서버가 다운돼도 재시작 후 데이터를 복구할 수 있다 | 중점 5 (Optional) |

### Phase 1 · 파일 단위로 각자 구현

- 파일 단위로 큰 틀만 맞추고 세부 설계와 구현은 각자 진행
- AI에 맡기는 작업의 범위와 구체성, 팀원마다 중점적으로 고민한 부분이 달랐음
- 코드 구조부터 차이가 있어 결과물을 공유할 때 각자의 구현 방식을 이해하고 비교하기 어려웠음

### Phase 2 · 같은 AI 초안에서 출발

- 팀원들이 같은 범위를 볼 수 있도록 AI로 공통 초안을 먼저 생성
- AI가 내린 선택을 하나씩 확인하고, 필요한 부분을 빼거나 더하거나 바꾸는 방식
- 초안이 모범 답안에 가까워 개선점을 찾기 어려웠고, 답을 보기 전에 직접 고민할 기회가 적었음

### 검증

- 시나리오와 기댓값을 직접 작성, ai 로 테스트 케이스를 만들어 실행
- 버튼 연타나 입력 중 목록 삭제처럼 직접 조작할 수 있는 동작은 수동으로도 확인
- 검증 과정에서 구현할 때 놓친 엣지 케이스 발견
- [테스트 시나리오와 기댓값 27개](#테스트-시나리오와-기댓값)

### 향후 계획 · Redis

- Redis를 사용하는 코드를 직접 작성해 실제 개발 상황을 경험
- 그 경험을 바탕으로 필요한 동작과 요구사항을 구체화
- 정리한 요구사항을 하나씩 AI와 함께 구현

### Phase 1·2 시연

- **Phase 1** · 내부 동작을 볼 수 있도록 구성. 테스트 영역에서 글자 수정 → Diff 확인 → Patch 적용 → 실제 DOM과 입력값 확인. [Virtual DOM, Diff & Patch](pages/demo/index.html)
- **Phase 2** · 실제 사용 상황에 가까운 영화 예매 화면으로 구성. 좌석 선택 → 합계와 남은 시간 확인 → 예매 확정. [영화관 좌석 예매](pages/demo/cinema-booking.html)

## 테스트 시나리오와 기댓값

아래 표는 테스트 실행 전에 사람이 정한 기댓값입니다. 출처는 시나리오를 가져온 곳이며, 실제 관측값은 [테스트 페이지](tests/index.html)에서 확인할 수 있습니다. R-ID는 [요구사항](docs/requirements.md)의 ID입니다.

| ID | R-ID | 시나리오 | 출처 | 기댓값 |
| --- | --- | --- | --- | --- |
| T01 | R1 | 카운터 +1 버튼을 한 번 누른다. | 명세 | 화면 숫자가 1이 된다. |
| T02 | R1 | +1 버튼을 아주 빠르게 20번 누른다. | AI 후보 | 클릭이 각각 처리되면 초기 렌더를 제외하고 20번 렌더한다. 한 작업 안에서 `click()`을 20번 연속 호출하면 숫자는 20이 되고 한 번 렌더한다. |
| T03 | R1 | 한 클릭 핸들러에서 `setN(n + 1)`을 두 번 호출한다. | AI 후보 | 두 호출을 모아 한 번만 렌더한다. |
| T04 | R1 | `setN(n)`으로 현재 값과 같은 값을 설정한다. | AI 후보 | 추가 렌더와 DOM 변경이 없다. |
| T05 | R2 | 같은 상태로 컴포넌트를 두 번 실행한다. | 명세 | 같은 구조와 값을 가진 VDOM이 나온다. |
| T06 | R2 | 조건에 따라 `false`나 `null`을 자식으로 넘긴다. 예를 들어 `cond && h('p', …)`를 사용한다. | AI 후보 | 해당 위치에 자식 노드가 생기지 않는다. |
| T07 | R3 | 입력창에 글자를 쓰는 중 목록의 다른 항목을 삭제한다. | AI 후보 | 입력창과 입력값이 유지되고 해당 항목만 삭제된다. |
| T08 | R3 | 글자 하나를 바꾼다. | 명세 | Diff 변경 1건, 실제 DOM 조작 1회가 발생한다. |
| T09 | R3 | 목록 맨 앞에서 두 항목을 연속으로 삭제한다. | 명세 | Patch 결과가 새 VDOM을 처음부터 그린 결과와 같다. |
| T10 | R3 | `class` 속성을 지운다. | 명세 | Diff가 속성 제거를 감지하고 실제 DOM에서도 속성이 사라진다. |
| T11 | R3 | 목록 1,000개 중 한 항목만 바꾼다. | AI 후보 | Diff에 해당 항목의 변경만 잡힌다. |
| T12 | R4 | 같은 컴포넌트를 서로 다른 props로 재사용하고 전달한 값을 바꾼다. | AI 후보 | Diff에 `PROPS` 변경이 잡히고, 기존 노드를 유지하면서 바뀐 속성을 반영한다. `REPLACE`보다 DOM 조작 비용이 낮아야 한다. |
| T13 | R5 | 자식 컴포넌트에서 `useState`를 호출한다. | 명세 | 에러가 발생한다. |
| T14 | R5 | 자식 컴포넌트가 도우미 함수를 통해 `useState`를 호출한다. | 명세 | 도우미 함수를 거쳐도 에러가 발생한다. |
| T15 | R5 | 앱에서 `TodoItem({...})`처럼 컴포넌트를 직접 호출한다. | 명세 | 글자 검사에서 직접 호출을 잡는다. `// allow-direct-call`을 붙인 줄은 통과한다. |
| T16 | R5 | 자식이 부모가 넘긴 함수로 할 일을 삭제한다. | 명세 | 할 일 개수와 목록이 함께 바뀐다. |
| T17 | R6 | `useEffect`에서 값을 바꾸는 `setState`를 호출하고 `deps`를 생략한다. | AI 후보 | 렌더마다 effect가 실행되고 상태 갱신이 이어진다. |
| T18 | R6 | `useEffect`에서 `setState`를 호출하고 `deps`로 `[]`를 준다. | AI 후보 | 첫 렌더 뒤 effect가 한 번 실행되고, 그로 인한 추가 갱신도 한 번 일어난다. |
| T19 | R6 | effect가 실행되는 시점을 확인한다. | 명세 | DOM에 화면 변경을 반영한 뒤 effect가 실행된다. |
| T20 | R6 | `deps`를 바꿔 effect를 다시 실행한다. | 명세 | 이전 effect의 정리 함수가 먼저 실행된다. |
| T21 | R7 | `deps`가 같은 상태에서 다시 렌더한다. | 명세 | `useMemo`가 이전 계산값을 재사용한다. |
| T22 | R7 | `deps`에 매 렌더 새 배열이나 객체를 넣는다. | AI 후보 | 실행 시 참조가 매번 달라 다시 계산하며 결과값은 맞다. 글자 검사는 `deps` 배열 안의 객체·배열 리터럴과 `.filter()`·`.map()` 직접 호출을 잡는다. `[n]`, `[todos]`, `// allow-direct-call`이 있는 줄은 통과한다. `const o = { n }` 뒤 `[o]`를 넘기는 경우는 검사가 잡지 못한다. |
| T23 | R8 | 체크된 항목이 있는 목록 맨 앞에 새 항목을 추가한다. 항목을 만들 때 랜덤 ID를 한 번 부여해 `key`로 쓴다. | AI 후보 | 모든 항목에 `key`가 있고, 앞에 항목을 추가해도 기존 항목의 `key`와 체크 상태가 유지된다. |
| T24 | R8 | 목록의 항목 1,000개에 `key`를 부여한다. | AI 후보 | `key` 1,000개가 모두 서로 다르다. |
| T25 | R8 | `key`가 있는 목록 맨 앞에 항목을 추가한다. | 명세 | 새 항목만 추가 변경으로 잡히고 기존 항목은 유지된다. |
| T26 | R8 | `h(TodoItem, { key })` 대신 `TodoItem`이 반환하는 `li`에 `key`를 붙인다. | AI 후보 | `li`의 `key`로 기존 항목을 식별한다. 맨 앞에 항목을 추가하면 `CREATE` 1건이 생긴다. 양쪽에 `key`가 있으면 `li`의 값을 사용한다. |
| T27 | R9 | 한 핸들러에서 서로 다른 상태의 setter를 각각 호출한다. | AI 후보 | 두 상태 변경을 한 번의 렌더로 반영한다. |

## 로컬에서 열기

저장소 루트에서 서버를 실행합니다.

```bash
npx serve .
```

기본 포트 3000으로 실행한 경우 아래 주소에서 엽니다.

- Phase 1 · `http://localhost:3000/pages/demo/`
- Phase 2 · `http://localhost:3000/pages/demo/cinema-booking.html`
- 공통 테스트 · `http://localhost:3000/tests/`
