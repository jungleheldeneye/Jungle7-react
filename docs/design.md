# 미니 React 명세 (작성 중)

> 이 문서는 **"무엇을 주고, 그게 어떻게 동작한다고 약속하나"**까지만 정한다.
> 내부 모양(텍스트 노드 표현, 변경 목록 형식 등)은 각자 정하고 결정 기록에 한 줄 남긴다.
>
> 표시: ✅ 정함 · ❓ 열려 있음 · 📝 각자 정하고 기록

## 1. 요구사항

### 배경: React가 없던 시절의 고통

데이터가 바뀔 때마다 **그 데이터를 보여주는 화면 요소를 개발자가 직접 찾아서 고쳐야** 했다.

- 한 곳이라도 빠뜨리면 → 화면과 데이터가 어긋난다
- 그게 싫어서 전체를 다시 그리면 → 느리고, 입력하던 값이 사라진다

```js
// 데이터를 바꿀 때마다 화면도 손으로 고쳐야 함
n = n + 1
document.getElementById('count').textContent = n
```

### 요구사항 목록

| ID | 우선 | 요구사항 | 해결 방법 |
| --- | --- | --- | --- |
| **R1** | Must | 데이터만 바꾸면 화면이 자동으로, 일관되게 따라온다 | `setState` |
| **R2** | Must | 개발자는 "데이터가 이럴 때 화면은 이렇게 생겼다"만 적는다 | 컴포넌트 = 함수 |
| **R3** | Must | 다시 그려도 빠르고 입력값이 유지된다 (필요한 것만 다시 그리기) | VDOM + Diff + Patch |
| **R4** | Must | 화면을 재사용 가능한 조각으로 나눌 수 있다 | 컴포넌트 + props |
| **R5** | Must | 데이터가 어디 있고 어디서 바뀌는지 예측할 수 있다 | Lifting State Up, 단방향 흐름, 자식 `useState` 금지(실행 중 검사) |
| **R6** | Must | 화면이 그려진 뒤, 필요할 때만 부수 작업을 실행한다 | `useEffect` |
| **R7** | Must | 바뀐 게 없으면 지난 계산 결과를 재사용한다 | `useMemo` |
| **R8** | Should | 리스트 순서가 바뀌어도 최소한만 갱신한다 | `key` |
| **R9** | Could | 여러 상태 변경을 한 번의 다시 그리기로 묶는다 | Batching |

> **모든 코드는 이 중 하나 때문에 존재해야 한다.** R-ID를 댈 수 없는 코드는 넣지 않는다 (오버엔지니어링 방지).

## 2. 명세

### 전체 흐름

**처음 그리기**

```
render(Counter, app)                              component.js
  → Counter() 실행 → h()가 VDOM을 만듦             vdom.js        R2
  → h(자식, props)로 적힌 자식 컴포넌트를 라이브러리가
    "지금 = 자식"이라고 표시한 뒤 직접 실행해서 펼침   component.js   R4, R5
  → vdomToDom(VDOM) → 실제 DOM을 통째로 만들어 붙임   vdom.js
  → effect 실행                                    hooks.js       R6
```

**다시 그리기** (setState가 불렸을 때)

```
setN(1)                                           hooks.js       R1
  → Counter() 다시 실행 → h()가 새 VDOM을 만듦       vdom.js        R2
  → 자식 컴포넌트도 같은 방식으로 펼침               component.js   R4, R5
  → diff(옛 VDOM, 새 VDOM) → 변경 목록              diff.js        R3, R8
  → patch(실제 DOM, 변경 목록) → 바뀐 곳만 고침       patch.js       R3
       └ 새로 생긴 노드(CREATE)·통째로 바뀐 노드(REPLACE)만 vdomToDom
  → effect 실행 (deps가 바뀐 것만)                  hooks.js       R6
  → 새 VDOM을 "옛 VDOM"으로 보관 (다음 비교용)
```

> `domToVdom`은 이 흐름에 없다. 이미 있는 HTML에서 시작할 때(phase1 페이지)와 왕복 테스트에서만 쓴다.

### 2-1. 공개 API — 사용하는 쪽이 쓰는 것

#### `h(type, props, ...children)` → VDOM · vdom.js · R2, R4, R8
- 입력: 태그 이름 **또는 컴포넌트 함수**, 속성 객체(없으면 `null`), 자식들(문자열, 다른 `h(...)`, 또는 그 배열. 배열은 펴서 한 줄로 늘어놓는다: `todos.map(...)`을 `...` 없이 넘겨도 된다)
- 출력: VDOM 객체. **모양은 공개 약속이 아니다.** 사용하는 쪽은 `h()`로만 만들고, 안을 열어보거나 직접 만들지 않는다. 모양은 언제든 바뀔 수 있다
- 보장
  - [ ] 같은 입력이면 같은 VDOM이 나온다
  - [ ] props의 `key`는 실제 DOM 속성이 아니라 리스트 구분용으로만 쓰인다 (R8)
  - [ ] `h(TodoItem, props)`는 TodoItem을 바로 실행하지 않는다. "이거 불러줘" 메모만 만들고, 실행은 라이브러리가 한다 (R5)
- 규칙 (4번 열린 질문 4 결정)
  - 대문자로 시작하는 함수는 컴포넌트다. 반드시 `h(컴포넌트, props)`로 부르고, props는 객체 하나로 넘긴다
  - 그 외 함수는 도우미다. 직접 불러도 된다
- 직접 호출 검사 (글자 검사, 테스트 실행 때 한 번)
  1. 대상: 앱 코드(사용 예시, phase 페이지). 라이브러리 코드와 테스트 파일은 제외 (테스트는 컴포넌트를 직접 불러 확인해도 됨)
  2. 컴포넌트 이름 모으기: `function 대문자이름`, `const/let 대문자이름 =`로 정의된 이름
  3. 실패 조건: 모은 이름 바로 뒤에 `(`가 오고, 앞에 `function`도 `.`도 없을 때
  4. 검사 전에 주석(`//`, `/* */`)은 지운다. 문자열은 그대로 검사한다
  5. 예외: 줄 끝에 `// allow-direct-call`이 있으면 그 줄은 검사하지 않는다
  - [ ] `TodoItem({...})` 직접 호출이 있으면 실패한다
  - [ ] `h(TodoItem, ...)`, `function TodoItem(`, `String(n)`은 실패하지 않는다
  - [ ] `// allow-direct-call`이 붙은 줄은 실패하지 않는다

#### `useState(초기값)` → `[현재 값, 바꾸는 함수]` · hooks.js · R1
- 입력: 시작값
- 출력: 두 칸짜리 배열. 이름은 사용하는 쪽이 붙인다 (`const [n, setN] = ...`)
- 보장
  - [ ] 다시 그려도 마지막 값을 돌려준다 (초기값은 처음 한 번만 쓴다)
  - [ ] 바꾸는 함수를 부르면 화면이 따라온다
  - [ ] 한 컴포넌트에 여러 개 있어도 서로 섞이지 않는다
  - [ ] 루트 컴포넌트(App) 밖에서 부르면 에러가 난다. 함수를 몇 번 거쳐서 불러도 잡힌다 (R5)

#### `useEffect(fn, deps)` · hooks.js · R6
- 입력: 실행할 함수(정리 함수를 돌려줄 수 있음), 의존 값 배열
- 보장
  - [ ] 화면이 바뀐 **뒤에** 실행된다
  - [ ] deps가 지난번과 같으면 실행하지 않는다
  - [ ] 다시 실행하기 전에 지난번 정리 함수를 먼저 부른다

#### `useMemo(fn, deps)` → 계산 결과 · hooks.js · R7
- 입력: 계산 함수, 의존 값 배열
- 출력: 계산 결과
- 보장
  - [ ] deps가 지난번과 같으면(참조 비교) fn을 다시 실행하지 않고 지난 결과를 돌려준다

#### `render(Component, 붙일 곳)` · component.js · R1, R3 · ❓ 이름
- 입력: 컴포넌트 함수, 실제 DOM 요소
- 보장
  - [ ] 처음 한 번 그린다
  - [ ] setState 때마다 컴포넌트를 다시 실행하고, **바뀐 부분만** 실제 DOM에 반영한다
  - [ ] 입력창에 쓰던 값이 다시 그린 뒤에도 남아 있다
  - [ ] 자식이 부모가 넘긴 함수로 데이터를 바꾸면, 그 데이터를 보는 화면이 전부 같이 바뀐다 (예: 삭제 시 개수와 목록이 함께) (R5)

### 2-2. 내부 모듈 — 팀끼리의 약속 (사용하는 쪽은 모름)

#### `domToVdom(dom)` / `vdomToDom(vdom)` · vdom.js · R3
- 방향: `domToVdom`은 실제 DOM을 **읽어서** VDOM으로, `vdomToDom`은 VDOM을 보고 실제 DOM을 **만든다**
- 보장
  - [ ] DOM → VDOM → DOM 왕복하면 원래 HTML과 같다 (공백·주석 포함, 6-2)

#### `diff(옛 VDOM, 새 VDOM)` → 변경 목록 · diff.js · R3, R8
- 보장
  - [ ] 둘이 같으면 빈 목록
  - [ ] 글자 하나 바뀌면 변경 1개
  - [ ] 사라진 속성도 변경으로 잡는다
  - [ ] key가 있으면 리스트 앞에 추가해도 기존 항목은 변경으로 잡지 않는다

#### `patch(실제 DOM, 변경 목록)` · patch.js · R3
- 보장
  - [ ] 결과가 새 VDOM으로 처음부터 그린 것과 같다
  - [ ] 앞에서 연속으로 삭제해도 맞다 (인덱스 밀림)
  - [ ] 변경 목록에 없는 노드는 건드리지 않는다 (→ 입력값 유지)

## 3. 사용 예시

### 카운터

```js
function Counter() {
  const [n, setN] = useState(0)
  return h('div', null,
    h('p', null, String(n)),
    h('button', { onclick: () => setN(n + 1) }, '+1')
  )
}

render(Counter, document.getElementById('app'))
```

- ✅ 컴포넌트 = 화면 모양을 돌려주는 **그냥 JS 함수** (R2)
- ✅ DOM을 직접 찾거나 고치는 코드는 사용하는 쪽에 없다 (R1)

### 할 일 목록

```js
function App() {
  const [todos, setTodos] = useState([])   // 데이터는 전부 App에만
  const [text, setText] = useState('')     // 입력 글자도 App으로 올림
  const add = () => { setTodos([...todos, { id: Date.now(), text }]); setText('') }
  const remove = (id) => setTodos(todos.filter(t => t.id !== id))

  return h('div', null,
    h('p', null, `할 일 ${todos.length}개`),
    h(TodoInput, { text, onInput: setText, onAdd: add }),
    h('ul', null, todos.map(t => h(TodoItem, { todo: t, onRemove: remove })))
  )
}

function TodoItem({ todo, onRemove }) {     // 상태 없음, 받아서 그리기만
  return h('li', { key: todo.id },
    todo.text,
    h('button', { onclick: () => onRemove(todo.id) }, '삭제')
  )
}

function TodoInput({ text, onInput, onAdd }) {   // 상태 없음
  return h('div', null,
    h('input', { value: text, oninput: (e) => onInput(e.target.value) }),
    h('button', { onclick: onAdd }, '추가')
  )
}
```

| 요구사항 | 사용하는 쪽에서 보이는 자리 |
| --- | --- |
| R4 조각 나누기 | 컴포넌트 여러 개를 `h(컴포넌트, props)`로 연결 |
| R5 데이터 위치 예측 | `useState`는 App에만. 자식은 `onRemove`·`onInput`으로 부모에게 부탁. 자식에서 `useState`를 쓰면 에러. 컴포넌트(`TodoItem`, `TodoInput`)는 대문자 이름 + `h()`로만 부름 |
| R8 key | `{ key: todo.id }` ❓ 위치는 6번 "컴포넌트 메모를 언제 펼치나"와 함께 정함 (`TodoItem` 안의 `li` vs `h(TodoItem, { key })`) |
| R3 입력 유지 | 목록이 바뀌어도 입력창의 글자가 남아 있어야 함 |

## 4. 열려 있는 질문 ❓

1. **자식 컴포넌트도 상태를 가질 수 있나?**
   - A. 가질 수 있다: 실제 React 방식. 컴포넌트마다 hooks 저장소를 따로 관리해야 함
   - B. App(루트)에만 있다: 저장소 하나라 단순, R5와 맞음. 한 곳에서만 쓰는 값도 App으로 올려야 함
   - 결정: ✅ **B. 라이브러리가 실행 중에 검사해서 막는다**
     - 막는 방법 후보: ① 규칙만 ② 테스트로 코드 글자 검사 ③ 실행 중 검사(자식이 `useState`를 부르면 에러) ④ props 잠그기 ⑤ 상태를 컴포넌트 밖 store로
     - ③을 고른 이유: ②는 이름을 바꾸거나 함수를 한 번 거치면(`useDeleted()`) 빠져나간다. 그렇게 쉽게 빠져나갈 수 있으면 "어디서 바뀌는지 예측할 수 있다"(R5)고 말할 수 없다. ③은 검사가 `useState` 안에 있어서 어떤 길로 와도 잡힌다
     - 대가: 자식을 `TodoItem(...)`으로 직접 부르지 않고 `h(TodoItem, ...)`으로 라이브러리에 맡겨야 한다. 입력 글자 같은 작은 값도 App으로 올려야 한다
     - ④는 다른 실수(자식이 `todo.text = 'x'`로 부모 데이터를 직접 고침)를 막는 것이라 보류 → 5. 비목표
2. **화면에 붙이는 함수 이름**: `render` / `mount` / 기타
   - 결정:
3. **이벤트 속성 이름**: `onclick`(DOM 그대로) / `onClick`(React처럼)
   - 결정: ✅ **`onclick` (DOM 그대로)**. 명세 예시와 같고 이름 변환이 필요 없다 (6-3 결정 기록)
4. **컴포넌트와 도우미 함수를 어떻게 구분하나** (1번 결정에서 나온 질문)
   - 배경: 1번의 실행 중 검사는 컴포넌트를 `h()` 없이 직접 부르면(`TodoItem({...})`) 빠져나간다. 그래서 "컴포넌트는 반드시 `h()`로 부른다"는 규칙이 필요하고, 그러려면 무엇이 컴포넌트인지 구분해야 한다
   - 도우미 함수(`굵게('중요')` 등)는 직접 불러도 괜찮다. 부른 쪽의 시간에 실행되므로 자식 안에서 도우미를 거쳐 `useState`를 불러도 잡힌다
   - 후보: A. 화면 조각 함수는 전부 `h()` / B. 대문자로 시작하면 컴포넌트 / C. `component()`로 감싸서 등록
   - 결정: ✅ **B. 대문자로 시작하는 함수 = 컴포넌트 → 반드시 `h(컴포넌트, props)`로 부른다. 그 외는 도우미 → 직접 불러도 된다**
     - 이유: 실제 React 관례와 같아서 설명하기 쉽다. 라이브러리 코드가 늘지 않는다. 이름만 보고 글자 검사로 직접 호출을 찾을 수 있다
     - 대가: 컴포넌트 이름은 영어로 지어야 한다(한국어엔 대문자가 없음). `String(`, `Number(` 같은 JS 기본 함수는 검사 예외로 둬야 한다
     - 남는 구멍: 컴포넌트를 소문자로 짓거나 다른 변수에 담아 직접 부르면(`const f = TodoItem; f()`) 못 잡는다. 일부러 해야 생기는 일이라 받아들인다. 기준은 **"실수는 막고, 일부러 깨는 것까지는 막지 않는다"**
     - C를 안 고른 이유: 직접 호출까지 실행 중에 막을 수 있어 가장 확실하지만, 공개 API(`component()`)가 하나 늘고 근거가 R5 하나뿐이다. 감싸기를 깜빡하면 결국 같은 구멍이 생긴다
   - 이어서 정한 것: 글자 검사를 정확히 어떻게 하나 (2-1 `h()`의 "직접 호출 검사")
     - 무엇을 컴포넌트 이름으로 볼까: ✅ **우리 앱에서 대문자로 정의한 이름만**. "대문자 + `(`" 전체를 보면 `String(`, `Error(`처럼 JS 기본 함수가 걸려서 끝없는 예외 목록이 필요하다
     - 문자열 안의 `TodoItem(`: (가) 문자열을 지우고 검사하면 백틱 `${TodoItem()}` 안의 진짜 호출을 놓친다. (다) 따옴표를 추적하면 정확하지만 `${ }` 안까지 다루느라 검사 코드가 JS 해석기만큼 커진다. ✅ **(나) 그대로 검사 + 예외 주석**: 놓치는 건 없고, 잘못 실패하면 줄 끝에 `// allow-direct-call`을 붙인다
     - 예외 주석을 둔 이유: 문자열에 컴포넌트 이름을 못 쓰면 자율성이 떨어진다(JS 설명 페이지 등). 주석으로 풀면 예외가 코드에 글자로 남아서 검색하면 다 나온다. 몰래 빠져나간 곳이 없으니 R5의 "예측할 수 있다"와도 맞는다
     - 비용 메모: 글자 검사는 테스트 때 한 번 파일을 훑는다(O(코드 길이)). 앱 실행 중에는 돌지 않는다. 실행 중 비용은 `useState`의 `if` 한 줄(O(1))뿐이다

### 6-1. 결정 기준 (예나)

- 결정 기록 형식: **후보 → 이유 → 대가 → 남는 구멍 → 성능 영향(차수 / 상수 / 없음)**
- 층마다 우선하는 것이 다르다
  - 공개 API(쓰는 사람): 편함 (R2). 팀 원칙: **쓰는 사람이 편하게**
  - 실행 횟수·DOM 조작 수·노드 수를 바꾸는 내부 결정(차수): 성능 (R3)
  - 노드 하나당 상수만 바꾸는 내부 결정: 우리가 읽고 검증하기 쉬움 (설명 못 하는 줄은 승인 안 함)
- 상수 비용이 쌓이는 건 추측 말고 측정으로 잡는다: "할 일 1000개에서 하나 바꿨을 때 diff + patch가 16ms(한 프레임) 안" 테스트
- 반복해서 나온 패턴: **특별 취급은 입구(`h()`, `domToVdom`) 한 곳에 모으고, 뒤의 모듈(diff·patch·vdomToDom)은 신경 쓰지 않게 한다**

### 6-2. VDOM 모양 결정 (예나)

최종 모양:
```js
{ type: 'li', props: { class: 'done' }, key: 3, children: [{ type: '#text', ... }, { type: 'button', ... }] }  // 요소
{ type: '#text', props: { nodeValue: '밥' }, children: [] }                                                 // 텍스트
{ type: '#comment', props: { nodeValue: ' 목록 ' }, children: [] }                                          // 주석
```

**텍스트 노드 표현: ✅ B. 주석처럼 객체로 감싼다** (`{ type: '#text', props: { nodeValue: '할 일 3개' }, children: [] }`)
- 후보: A 문자열 그대로 / B `{ type: '#text', props: { nodeValue }, children: [] }`로 감싸기
- 처음엔 A였다가 B로 바꿨다: 주석은 문자열로 둘 수 없어서(글자와 구분이 안 됨) 이미 객체인데, 글자만 문자열이면 모양이 두 가지가 된다
- 이유: 6-1 패턴("특별 취급은 입구에 모은다")에 맞는다. 문자열을 감싸는 일은 입구(`h()`, `domToVdom`)에서만 하고, 뒤 모듈(diff·patch·vdomToDom)은 모든 노드를 `type`/`props`/`children`으로 똑같이 다룬다. 글자 변경도 주석처럼 `nodeValue` 속성 변경(PROPS)으로 잡혀서 diff에 문자열 분기가 없다. diff 케이스는 4개(TEXT가 PROPS에 합쳐짐)
- 대가: 테스트 기대값과 디버깅 출력이 길어진다 → 테스트는 결과(변경 개수, patch 결과 HTML)로 확인해서 줄인다. `h()`에 문자열 자식을 감싸는 줄 1개
- 남는 구멍: `h()`를 거치지 않고 VDOM을 손으로 만들면서 자식에 문자열을 넣으면 뒤 모듈이 처리하지 못한다. VDOM은 `h()`나 `domToVdom`으로만 만든다
- 성능 영향: 상수 (글자 노드마다 객체 1개, 전체 O(n) 그대로)

**공백 노드: ✅ A. 전부 둔다**
- 후보: A 전부 둔다 / B 공백만 있는 노드를 버린다 / C 줄바꿈 섞인 공백만 버린다 (JSX 규칙)
- 이유: 쓰는 사람이 적은 HTML이 그대로 동작한다(팀 원칙). 화면을 100% 지키는 규칙은 A뿐이다(브라우저의 공백 표시는 CSS `white-space`까지 봐야 앎). 왕복 보장이 그대로다. VDOM과 실제 DOM의 자식 개수가 같아서 path가 어긋나지 않는다
- 대가: phase1 페이지에서 노드 수가 약 2배
- 남는 구멍: 없음 (B는 `<b>예나</b> <i>님</i>`이 붙고, C는 줄바꿈 공백과 `<pre>`가 깨짐)
- 성능 영향: phase1 경로에서만 노드 수 증가. `h()`에는 공백 노드가 없어서 실제 앱 흐름엔 영향 없음
- 실제 React와 비교: React에는 `domToVdom`이 없다. 공백은 입구(JSX 컴파일러)에서 C 규칙으로 정리하고, 필요한 공백은 개발자가 `{' '}`로 적는다. 그래서 diff/patch는 공백을 신경 쓰지 않는다. 우리는 `domToVdom`이라는 입구가 하나 더 있어서 A를 골랐다

**주석 노드: ✅ 둔다** (`{ type: '#comment', props: { nodeValue }, children: [] }`)
- 후보: 둔다 / 버린다
- 이유: VDOM과 실제 DOM의 자식 개수가 항상 같아서 path가 어긋나지 않는다. 왕복 보장이 그대로다. 요소와 같은 모양이라 diff에 새 코드가 필요 없다 (요소 ↔ 주석은 type이 달라 REPLACE, 글자 변경은 PROPS)
- 대가: `domToVdom`·`vdomToDom`에 분기 1개씩, patch에서 `nodeValue`를 property로 넣기 (주석·글자 노드에 `setAttribute`를 부르면 에러)
- 남는 구멍: 없음 (버리면 path를 세는 모든 곳에서 주석 건너뛰기를 기억해야 하고, 빠뜨리면 엉뚱한 노드가 고쳐지는 조용한 버그)
- 성능 영향: 없음에 가까움. 주석은 phase1 HTML에만 있고 `h()`에는 없음
- 개발자가 쓴 주석이 없어지나?: JS 주석은 DOM에 안 들어가서 상관없다. HTML 소스 파일의 주석도 그대로다. 버렸다면 바뀌는 건 브라우저 DOM(개발자 도구)뿐이었다
- 참고: 글자도 같은 객체 모양(`#text`)이라, 주석을 위해 따로 만드는 코드는 `type` 이름만 다르다

**key 위치: ✅ B. 최상위로 꺼낸다** (`{ type, props, key, children }`)
- 후보: A props 안에 그대로 / B `h()`에서 꺼내 최상위로
- 이유: props를 반복문으로 도는 곳(`vdomToDom`, `diff`의 props 비교, `patch`)마다 `if (name === 'key') continue`를 넣지 않아도 된다. 특별 취급이 `h()` 한 곳에 모인다. 실제 React와 같다 (자식 컴포넌트가 `props.key`를 읽으면 `undefined`)
- 대가: `h()`에 한 줄 (`const { key, ...rest } = props || {}`)
- 남는 구멍: 없음 (A는 props 도는 곳을 하나라도 빠뜨리면 `key="3"`이 실제 DOM에 생김. 나중에 props를 도는 코드가 늘면 거기도 기억해야 함)
- 성능 영향: 없음
- 참고: `domToVdom`으로 읽은 VDOM은 key가 항상 `undefined`다 (실제 DOM에는 key가 없음). phase1 페이지는 key 없이 위치로 비교한다

### 6-3. 그 외 결정 기록

정한 것은 여기에 한 줄로 남긴다 (결정 → 이유 → 대가).

- **속성 넣기**: `vdomToDom`에서 함수는 property(`el.onclick = fn`), 글자·주석의 `nodeValue`도 property(6-2), 나머지는 `setAttribute`. 왕복 결과가 원래 HTML과 같다. 대가: `value`를 property로 바꾸는 처리는 `patch`에서 다시 정해야 한다
- **이벤트 이름**: `onclick` (DOM 그대로, 열린 질문 3). 명세 예시와 같고 이름 변환이 필요 없다
- **배열 자식**: `h()`가 배열 자식을 한 단계 편다 (`h('ul', null, todos.map(...))`). 공개 API는 쓰는 사람이 편하게(6-1): `...`을 빠뜨리는 실수가 없어지고, 펼쳐서 넘겨도 그대로 동작한다. 대가: `h()`에 한 줄. 배열 안 자식에 key가 없을 때 알릴 수 있게 됐지만, 경고는 아직 만들지 않는다
